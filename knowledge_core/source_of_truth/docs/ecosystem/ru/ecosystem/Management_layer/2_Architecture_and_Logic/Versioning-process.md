# ♻️ Процесс версионности

Версионность — это способ фиксировать состояние системы во времени.

Она помогает участникам экосистемы понимать:

- какой этап развития уже достигнут и какие правила и подходы действуют сейчас;
- где находится новая редакция, если документ уже вынесен на пересмотр.

## Что такое SemVer в классическом понимании

В индустрии разработки программного обеспечения широко используется Semantic Versioning.

Классическая версия записывается так:

```text
MAJOR.MINOR.PATCH -> например, 1.4.2
```

В DET / DETai эта идея используется не буквально, а как отправная точка. Нам важно не только техническое изменение, но и изменение состояния проекта, документа, правила или процесса.

## Как версионность работает в DET / DETai

Экосистема DET / DETai версионирует не только код.

Версия может фиксировать:

- состояние проекта;
- состояние документа;
- состояние правила;
- состояние процесса;
- состояние смысловой рамки, по которой работают люди и AI-агенты.

Практические форматы версий и обязательные правила повышения версии описывает [Versioning Standard](https://docs.detai-x.com/ru/ecosystem/Management_layer/3_Technical_Standards/Versioning-standard/).

Проектная логика версий описана отдельно в [♻️ Процесс версионности в U.L.I.](https://docs.detai-x.com/ru/ecosystem/DETai/U.L.I/3_Technical_Standards/Versioning-in-U.L.I/).

## Версия как этап развития

Ключевой принцип:

> версия повышается не автоматически, а по управленческому решению.

Это означает:

- завершён логический этап развития;
- система достигла устойчивого состояния;
- команда признаёт этот этап завершённым;
- новая версия может стать точкой отсчёта для следующего цикла.

Для проекта версия фиксирует состояние системы. Для документа версия фиксирует состояние знания или правила, по которому система действует.

## Версионность как форма обучения

Каждый документ — это часть обучающего цикла экосистемы.

Когда процесс или структура больше не соответствуют реальной практике, мы обновляем документацию, а значит обновляем контекст, по которому дальше будут действовать люди, Codex, Custom GPT и другие AI-агенты.

Работа над новой редакцией не отменяет действующую опубликованную версию. Git сохраняет исходное состояние, ветка и PR показывают предлагаемые изменения, а Team OS связывает работу, обсуждения и результаты.

## Два слоя статусов

| Слой | Что описывает | Источник |
|---|---|---|
| Metadata документа | Жизненный цикл текста, его версию и отдельно каноническую силу | YAML front matter в Knowledge Substrate |
| Редакционная работа | Подготовку, review и публикацию новой редакции | PR и связанные рабочие записи Team OS |

`active` означает действующую версию документа, а `draft` — рабочий текст для review. Каноническая сила определяется отдельно через `governance.canonicality`. Статус задачи, заметки или PR не присваивает документу нормативную силу.

Материалы новых редакций собираются в Note List [«Новые версии документов»](https://team.detai-x.com/task-center/lists/ccfaa624-198d-52c8-9d40-bb6c719b0833). Это список заметок; задачи исполнения и рабочие журналы имеют собственные типы и маршруты. Исторические стадии BASELINE, DRAFT или READY FOR PUBLICATION помогают понимать прежний редакционный процесс, но не являются универсальным workflow для всех объектов Team OS.

## Как выглядит цикл пересмотра

1. Исходная редакция фиксируется ссылкой на файл и commit SHA.
2. Новая редакция готовится в ветке и проходит review через PR.
3. Проверяются смысл, версия, metadata, ссылки и навигация.
4. Принятая редакция публикуется по правилам репозитория; предыдущая остаётся в Git history.
5. Рабочие записи Team OS связываются с итоговым PR и опубликованным документом.

Так Knowledge Substrate хранит версии знаний и правил, а Team OS — операционную работу вокруг их изменения. Полный текст документа не требуется дублировать в task-системе. Обязательные действия и условия повышения версии определяет [Versioning Standard](../3_Technical_Standards/Versioning-standard.md).
