# ♻️ Процесс версионности в U.L.I.

**Версия — признание нового устойчивого состояния проекта, а не счётчик изменений.** В U.L.I. её фиксируют осознанно, после завершения значимого этапа и прохождения Release Fixation.

Этот документ описывает **версии проектов и их выпускаемых компонентов**. Версии документов Knowledge Substrate регулируются отдельно: [Versioning Standard](https://docs.detai-x.com/ru/ecosystem/Management_layer/3_Technical_Standards/Versioning-standard/) и [процессом версионности документов](https://docs.detai-x.com/ru/ecosystem/Management_layer/2_Architecture_and_Logic/Versioning-process/).

## 1. Что означает новая версия

Версия закрепляет результат завершённого этапа развития:

- **Достигнутое состояние** — что стало возможным и чем система теперь отличается от предыдущей фиксации.
- **Состав изменений** — ключевые возможности, исправления, архитектурные решения и выполненные Work Packages.
- **Вклад в экосистему** — какой продуктовый, технический, инфраструктурный, образовательный, управленческий или иной ресурс усилился.
- **Проверенную устойчивость** — на каких результатах приёмки основано решение о выпуске и какие ограничения известны.

Merge PR, закрытие задачи, deployment и прошедшее время сами по себе **не повышают версию**. Между официальными версиями проект может развиваться через любое число коммитов и обновлений production; они отслеживаются по Git SHA и operational evidence.

## 2. Смысловая и техническая нумерация

Основная модель U.L.I. — **двухуровневая смысловая версия**:

```text
MAJOR.MINOR
```

| Пример | Значение |
| --- | --- |
| `0.1`, `0.2`, `0.x` | Завершённые этапы проекта, который ещё формируется; это не мешает внутреннему использованию. |
| `1.0` | Осознанное признание стабильного состояния, пригодного для устойчивой внутренней работы или публичной ответственности. |
| `1.1`, `1.2` и далее | Следующие устойчивые состояния через новые возможности, улучшения, исправления или архитектурное развитие. |

Переход к `1.0` **не требует** последовательного выпуска всех `0.x`. Номера отражают этапы зрелости, а не число PR. Решение о переходе к новому MAJOR или MINOR принимается по смыслу и результату Release Fixation, а не автоматически по правилам классического Semantic Versioning.

### Техническая версия пакета

Инструменты публикации и форматы пакетов иногда требуют три компонента `MAJOR.MINOR.PATCH`. Это **техническое представление**, которое не меняет основную двухуровневую модель U.L.I.

Например, смысловая версия **Team OS Plugin 1.2** может соответствовать версии пакета **`1.2.0`**. Для нового смыслового этапа по умолчанию используется `PATCH=0`; следующий `PATCH` допускается для отдельного технического выпуска исправленного пакета без объявления этапа `1.3`.

Обычные изменения сервера или исходников, не сопровождающиеся переизданием пакета, не обязывают повышать его техническую версию. **Изменённый пакет нельзя выдавать за прежний идентичный выпуск**: при повторной публикации следует соблюдать правила версий используемого канала.

## 3. Один проект, несколько выпускаемых компонентов

В типичном технологическом контуре один репозиторий соответствует одному проекту. **Монорепозиторий не нарушает этот принцип**: один проект может содержать несколько взаимосвязанных, но самостоятельно выпускаемых компонентов (*releasable components*).

Компонент — это отдельная поверхность поставки или использования (например, Web, Plugin, Mobile), а **не новый самостоятельный проект**. Общие Core, API, библиотеки и база данных могут обслуживать несколько компонентов.

**Пример — [DETai Team OS](https://github.com/DETai-org/team-os)**: один проект и один монорепозиторий с несколькими компонентами.

| Компонент Team OS | Назначение | Версионирование |
| --- | --- | --- |
| **Web** | Интерфейс в браузере | Собственная последовательность релизов |
| **Plugin** | Интерфейс ChatGPT через MCP и skills | Собственная последовательность релизов |
| **Mobile** *(возможный будущий компонент)* | Мобильное приложение | Собственная последовательность релизов при его появлении |
| **Core/API** | Общий технологический фундамент | Версии контрактов и совместимости; отдельная линейка релизов необязательна |

Для таких компонентов допускается **Independent Versioning — независимое версионирование**: Web и Plugin могут иметь разные номера и даты выпуска, сохраняя единый `main` и общую историю Git. Каждое семейство релизов задаётся локальным стандартом проекта; например, в Team OS используются форматы `web/vX.Y.Z` и `plugin/vX.Y.Z`. Это примеры **форматов тегов**, а не утверждение, что конкретные теги уже опубликованы.

Любой Git-тег указывает на **коммит монорепозитория целиком**, даже когда обозначает выпуск одного компонента. Несколько тегов могут указывать на один SHA. Совместимость общих модулей проверяется для затронутых компонентов, но изменение Core не требует автоматически выпуска новых версий каждого интерфейса.

[Локальный стандарт версионирования Team OS](https://github.com/DETai-org/team-os/blob/main/docs/standard/versioning-and-releases.md) уточняет семейства тегов, правила публикации и учёт production SHA. Общий принцип U.L.I. определяет, **когда состояние достойно версии**; локальный стандарт — **как его фиксировать технически**.

## 4. Когда и как фиксируется релиз

Решение о новой версии принимается по завершении этапов производственного цикла:

```text
Project Intent → Work Model Planning → Implementation → Release Fixation
```

В Work Model Planning и Implementation работа проходит через Epic Issue, Work Packages, ветки и PR. На этапе **Release Fixation** проверяют достигнутое состояние, обязательные результаты, качество, совместимость и ограничения.

Основанием для новой фиксации может стать завершённая архитектура, важный Epic Issue, устойчивый пользовательский сценарий, устранение критического ограничения или новый вклад в экосистему. **Ни одно из этих событий само по себе не заменяет приёмку.**

Возможные решения: релиз одобрен, заблокирован или принят с документированными некритичными ограничениями. Порядок проверки и критерии определяет [Release Fixation Standard](https://docs.detai-x.com/ru/ecosystem/DETai/U.L.I/3_Technical_Standards/release-fixation-standard/).

После одобрения для соответствующего проекта или компонента фиксируются, когда применимы:

1. Точный Git SHA и Git tag.
2. GitHub Release с кратким **Release Summary**: достигнутое состояние, изменения, проверка, ограничения и переносимые задачи.
3. Ссылки на Epic Issue, Work Packages и PR.
4. README, release notes и production evidence, если они требуются.

**Коммит → deployment → Release Fixation — не обязательная последовательность на каждую правку.** Деплой может происходить без нового официального релиза; GitHub Release и deployment обозначают разные события.

## 5. Версия проекта и статус продукта

**Проект, репозиторий, выпускаемый компонент и продукт — разные понятия.** Версия сама по себе не делает внутреннюю систему рыночным продуктом.

- Внутренний инфраструктурный проект может иметь устойчивую `1.0`, оставаясь внутренним.
- Публичный продукт требует не только стабильной версии, но и определённых аудитории, ценности, доступа, ответственного за поддержку и показателей наблюдения.
- После публичного выпуска разработка продолжается в том же проекте. Следующий этап становится новой публичной версией только после отдельной Release Fixation.

В контуре репозиторных продуктов U.L.I. смысловая `1.0` рассматривается как технический порог стабильности, **но не как достаточное основание для продуктового статуса**. Критерии продуктового объекта раскрывает [Модель продуктового объекта](../../../../product-market/product-object-model.md).

## 6. Принцип управления версиями

Версионность объединяет три решения:

- **Управленческое:** команда признаёт достижение нового состояния.
- **Коммуникационное:** участники и пользователи понимают, что изменилось.
- **Техническое:** зафиксированы проверяемые Git-артефакты и состояние поставки.

Номер версии не заменяет оценку результата, а наличие тега не доказывает фактическую публикацию или обновление production.
