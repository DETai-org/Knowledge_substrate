# Стандарт декларативной конфигурации Telegram-ботов DETai

**Функция:** `standard`. Нормативная модель для Telegram-ботов DETai независимо от языка и библиотеки (Python/Aiogram, TypeScript/Node.js и других). Она определяет, *где находится источник параметра, кто может его менять и как приложение подтверждает применение*. Реализация конкретного продукта должна соответствовать правилу, но выбор JSON или TOML может зависеть от его стека.

## 1. Видимая конфигурация и одна точка входа

- Рядом с приложением располагается каталог `config/` с коротким `README.md`: список **реально читаемых** файлов, назначение каждого, профиль экземпляра, способ выбора окружения и ссылки на нормативные документы. README — навигация, не копия значений из файлов.
- **Несекретные параметры** хранятся декларативно в типизированных структурированных файлах: предпочтительно **JSON для TypeScript/Node.js**; **TOML или JSON для Python** с проверенным парсером. Использование `.env` как основного перечня режимов, ролей, списков людей и не-секретных переключателей не допускается для новых реализаций.
- Не создавать демонстрационный `bots.json` или `admission.json`, который не читает исполняемый код. Не поддерживать одновременно JSON и `BOT_MODE`/список ID из env как два равноправных источника. Каждое правило имеет **одного владельца** и конкретную цепочку `файл → загрузчик → проверка → сервис`.
- **Владелец продуктового конфига** — owning repository приложения; host/network bindings и инвентарь инфраструктуры могут принадлежать отдельному [операционному контуру Infrastructure](../../../../Infrastructure/index.md). Наличие config-файла в Git и применённое состояние сервера — разные факты.
- Типовая (не обязательная по именам) декомпозиция — `bots.json` (экземпляры и режимы), `admission.json` (группы допуска), `runtime.json` (несекретные сервисные настройки), `secrets.env.example` (шаблон без значений). Маленькому боту допустим **один** структурированный конфигурационный файл с разделами; разносить настройки только ради количества файлов не требуется.
- **Идентификатор и username бота, публичные URL, окружение и режим работы не являются секретами сами по себе.** Однако Telegram ID/username людей относятся к идентификаторам пользователей: их реестры не следует публиковать в публичной базе знаний; использование в приватном Git допустимо лишь с ограниченным доступом и согласованными правилами обработки данных.

## 2. Профили и независимые оси

Явно разделять:
- **Экземпляр бота**: DEV/Production (реальный bot ID, username, выбор соответствующего токена).
- **Техническое окружение**: development/test/pilot/production, границы SQL, хранилища и провайдеров.
- **Аудиторию**: development/pilot/public — кто может войти в экземпляр. Бот в техническом production может оставаться закрытым для пилота.
- **Продуктовые права и роли**: Free/Plus/Pro, администратор продукта и служебные grants вычисляются в их **собственном** backend/SQL; проход в закрытый бот не даёт автоматически право модерации, оплату или подписку.

Списки входного допуска, например `admins`, `trusted`, `pilot`, должны быть именованы по **назначению**, а не смешаны в одной строке ENV. Стабильные числовые Telegram ID предпочтительнее изменяемых usernames; username допустим только по фактическому аутентифицированному Telegram update, не по произвольному введённому тексту. Нельзя считать разрешение доступа к боту признаком связанного DETai Account.

## 3. Секреты и минимальный ENV

- Отдельный **приватный файл секретов на окружение продукта** — `secrets.env` или эквивалент; один физический источник может содержать Telegram token, SQL credentials, provider keys, API/Commerce service tokens и signing secrets для бота, API и worker. В каталоге Git разрешён только `secrets.env.example` с **именами и безопасными заполнителями**. Реальный `secrets.env` исключён из Git, находится в защищённом месте и не копируется в CI-artifacts или логи.
- **Один физический файл секретов не означает общую область доступа ко всем ключам.** Загрузчик выделяет каждому процессу только необходимые значения и проверяет обязательные ключи отдельно. Если процессы под одним OS-пользователем способны прочитать общий файл, это следует явно считать общей границей доверия, а не обещать изоляцию, которой нет.
- Переменные окружения остаются для **секретов и минимальных селекторов запуска** (выбранный config directory/profile/путь к secret file, необходимые OS-механизмы). Не требуется полностью запрещать верхний регистр имён переменных: запрещается **переносить несекретную декларативную модель в разрозненные ENV-строки**.
- Реальные credentials не встраивать в JSON, source code, systemd unit, README и Markdown-таблицы; по возможности не оставлять токен/ключи в аргументах командной строки и диагностических сообщениях.

## 4. Загрузчик, валидация и запуск

- Загрузчик принимает **явный профиль**, читает его конфигурацию, валидирует schema/version, допустимые режимы, типы ID, имена, дубликаты, обязательные поля, границы сервисов и отсутствие конфликтующих источников. Неверная или неполная конфигурация приводит к **fail closed** — не к молчаливому включению `public`, выдаче прав или подстановке production secret.
- Проверять `getMe().id` против ожидаемого **числового** Bot ID до изменения webhook или запуска polling. Изменяемое Telegram-имя не заменяет эту проверку.
- API, worker, сервис уведомлений, Commerce и диагностические CLI читают согласованную конфигурацию своих разрешённых секций. Изменение профиля запуска не должно самопроизвольно включать реальный checkout или финансовую операцию. Действующий backend policy/Commerce ledger остаётся отдельным источником прав и платежей.
- В `systemd` и аналогичных launchers допускаются **путь к конфигурации, профиль и путь к защищённому secret file**, но не конкурирующий набор режимов, тарифов и ID. Обновление Git **не** означает автоматическое изменение действующего сервиса: конфигурацию применяют через контролируемый deploy с подтверждением эффективного профиля.
- При миграции из старых ENV сначала составить карту `старое поле → новый единственный владелец`, проверить сохранение допущенных пользователей и профилей, затем **удалить старое активное чтение**. Нельзя оставлять два механизма «на всякий случай» или переходить на пустой список администраторов без явного решения.

## 5. Документация и владение

| Вопрос | Владелец |
| --- | --- |
| Где меняются настройки ботов, режимы, группы допуска | `config/README.md` → исполняемые JSON/TOML |
| Где лежит секрет, не раскрывая его | приватный файл окружения + `secrets.env.example`; README указывает путь/права без значений |
| Какие права даёт тариф или роль пользователя | проектный policy/API/SQL, не admission JSON и не клиентская кнопка |
| Что делает деплой или переключение аудитории | эксплуатационный runbook и зарегистрированное решение владельца |
| Почему выбрана архитектура и где текущие задачи | ADR в owning repository, задачи и журнал работы в Team OS |

Конфигурационный README не превращать в повторный системный стандарт и не вести в нём временную историю коммитов. Общие [правила создания Telegram-ботов](telegram-bot-creation-standard.md) и [передачи языка](language-handover.md) остаются независимыми от механизмов допуска и секретов.

**Внедрение:** это целевой стандарт для новых ботов и рефакторинга существующих; публикация стандарта **не означает**, что каждый бот DETai уже переведён на JSON, один секретный ENV или новый launcher. Реальное соответствие проверяется в owning repository и при отдельном cutover.
