# DETai Testing & Feedback Loop Standard

## Назначение

Один общий стандарт тестирования для разработки с AI-агентами в проектах DETai. Цель — **минимальная недублирующая система реальных гарантий** и короткий цикл «идея → изменение → обратная связь» без снижения безопасности, сохранности данных или доверия к релизам.

**Главный принцип:** проверяй устойчивый **наблюдаемый смысловой контракт**, а не текущее представление, временный текст, внутреннюю последовательность шагов или форму реализации. Исключение — когда точная форма сама является явно утверждённым, внешним, юридическим, доступностным или машинным контрактом.

## 1. Что делает тест оправданным

Новый или сохраняемый тест должен иметь ясный ответ на четыре вопроса:

1. **Invariant** — какое observable behavior, публичный контракт, состояние, ограничение прав или известную регрессию защищает?
2. **Failure** — какой реалистичный дефект останется незамеченным, если тест убрать?
3. **Surviving coverage** — какая существующая проверка уже гарантирует это и можно ли расширить/параметризовать её?
4. **Cost** — на каком самом дешёвом уровне можно доказать инвариант, какова цена запуска и сопровождения?

Если отдельной гарантии нет — не добавляй тест. Количество изменённых файлов, новая ветка, private helper или каждое действие агента **не** требуют нового теста. Новый тест не должен служить протоколом того, как AI писал код.

## 2. Смысловой контракт против ситуативного представления

**Предпочитать:** статус и допустимые переходы, отсутствие утечек private-данных, сохранённую revision, не более одного результата при повторном callback, правильного владельца, доступность пользовательского действия, соответствие схеме/формату/языку, graceful fallback.

**Не фиксировать по умолчанию:** точную фразу подписи, косметический emoji, порядок кнопок, промежуточный dict/DTO, имена private helpers, порядок вызовов моков, конкретный DOM-узел, если они не являются утверждёнными контрактами.

Пример Telegram: при отсутствии готового PNG нельзя предложить действие, требующее PNG, или запустить модерацию. Тестируй допустимые действия и состояние медиа; не требуй дословной фразы «Изображение ещё готовится». Если редактор поменяет текст без изменения поведения, тест не должен ломаться. Проверяй точный текст только для осознанного copy/legal/accessibility или протокольного контракта и обозначай это прямо в названии теста.

Если тест упал после разрешённого изменения текста, **не переписывай ожидаемую строку механически**. Сначала выясни, является ли строка контрактом; если нет — замени хрупкое assertion на семантическое или убери избыточное.

## 3. Test pyramid и рационализация

Используй самый дешёвый слой, способный доказать свойство:

1. Domain, pure functions, schemas и contracts;
2. Application/service и adapter integration;
3. Bot/router/UI integration;
4. End-to-end и реальные внешние системы (несколько жизненно важных lifecycle smoke).

Не проверяй всю матрицу unit-кейсов повторно через E2E. При одинаковом поведении нескольких locale/format/target используй параметры; отдельный case нужен, если риск/контракт отличаются. Не объединяй разные инварианты в гигантский god test ради уменьшения числа тестов.

Особенно защищай authorization, fail-closed, data integrity, idempotency, state transitions, persistence, schema migrations, revision/HEAD guards, внешнюю публикацию и оплачиваемые действия. Эти проверки нельзя удалять ради красивых показателей.

Каждое удаление/слияние тестов сопровождай картой «удалённая гарантия → оставшийся тест/контракт» либо обоснованием, почему полезной гарантии не было. Изменять бизнес-логику ради зелёного теста запрещено.

## 4. Risk-based verification: отдельно от создания тестов

**Изменение не означает обязательного запуска полного набора.** Сначала классифицируй diff, затем выбери минимальное доказательство:

| Изменение | Обычная проверка | Перед production/release |
| --- | --- | --- |
| Текст, локализация, визуал, документация | diff/формат/ручной preview при необходимости; без полного suite | Точечная приёмка изменённой поверхности |
| Локальный UX, навигация, безопасный refactor | релевантные lightweight/type checks и targeted tests на стадии, установленной проектом | Затронутые сценарии |
| Права, подписки, модерация, публикация, security | targeted contract + regression, при нужде SQL | Релевантные интеграционные gates |
| SQL migration, durability, authentication, production runtime | isolated DB/security/data-integrity checks | Migration rehearsal + соответствующие критические gates |
| Большой релиз/архитектурная интеграция | scoped integration | Full suite один раз на проверенном release commit |

Проект вправе быть строже: например, не запускать тесты во время обычной разработки, а выполнять их только при merge по запросу владельца. Такой режим фиксируется в проектной инструкции для тестов (обычно `tests/AGENTS.md`), а корневой `AGENTS.md` направляет агента к ней. Реальные npm/pytest scripts и CI должны соответствовать этому режиму.

## 5. Fast feedback и работа AI-агента

- **Edit loop:** прочесть ближайший контракт и покрытие → внести минимальную правку → показать результат; не запускать full suite «на всякий случай».
- **Merge preparation:** выбрать targeted checks по риску, зафиксировать точные команды и результат для неизменённого commit/diff.
- **Release gate:** один согласованный прогон полной необходимой матрицы плюс специализированные migration/security gates, без дублирующих запусков на том же SHA.
- Не повторять успешно пройденные проверки при неизменившемся артефакте и окружении; при изменении — перезапустить только затронутые.
- При падении теста сначала определить: product defect, brittle assertion, плохие fixture/test infrastructure или изменение контракта. Не лечить «красный тест» обновлением ожидаемой строки без доказательства.
- Flaky test — дефект; retries без диагностики не заменяют исправление.
- Не поднимать PostgreSQL, не вызывать Nexus, провайдера или реальные каналы при текстовом/визуальном изменении. Для тяжёлых тестов использовать isolated ephemeral data, когда риск этого требует.
- Push, PR, merge, deploy — **разные операции**. Агент не начинает SQL/full regression только потому, что пользователь попросил commit/push или создать PR. Явный запрос merge инициирует соответствующий risk-based gate, но не обязательно полный suite.

## 6. CI и package scripts должны соответствовать политике

Проектная инструкция по тестированию обозначает допустимые события и стадии проверок, а корневой `AGENTS.md` маршрутизирует к ней. Реальная конфигурация должна соответствовать проектному режиму. Нельзя одновременно запрещать автоматические тесты в инструкции и оставлять активные push/pull_request-triggered тесты.

Для owner-controlled проектов допустимы workflows только с manual **workflow_dispatch** (для release/rehearsal) либо отсутствие workflow. Не считать отсутствие включённых Actions доказательством того, что конфигурация безопасна: проверить YAML triggers и фактические недавние runs. В других проектах допускается быстрый автоматический gate, если он **явно утверждён** и обеспечивает ценный feedback. Не менять существующую защиту продакшна ради скорости без оценки последствий.

Названия скриптов прозрачны: **build** собирает, **check** проверяет типы/статику, **test:targeted**/аналог запускает тесты, **test:full** — полную матрицу. Исключения, где проверка является безопасностью собранного артефакта, должны быть явно описаны; скрытые heavy tests в build/check недопустимы.

## 7. Метрики и пересмотр

Сохраняй baseline и trend, а не произвольную квоту на количество тестов: test source / application source ratio, число test-файлов/cases, median и p95 времени targeted/full проверки, flaky rate, число каскадных изменений тестов при чистом refactor, duplication/surviving-coverage map, escaped critical regressions. Доля тестового кода в 36% **сама по себе не является превышением нормы**; критичны скорость, хрупкость, поддержка и качество гарантий.

Если suite медленна, сначала профилируй фактическое время. Разделяй fast/integration/e2e/slow и запускай тяжёлые тесты реже либо по изменённым контрактам; не удаляй уникальные security/durability гарантии. Любое предложенное сокращение требует сохранённой карты гарантий.

## 8. Инструкции агентов по слоям

- Корневой **AGENTS.md**: только **маршрутизатор**. Укажи путь к локальному `tests/AGENTS.md` и требуй его чтения при создании/изменении тестов **или выборе режима проверки**, даже если код меняется вне `tests/`. Не копируй сюда общие правила.
- **tests/AGENTS.md** (или эквивалент): короткая ссылка на этот канон и **только отличия проекта** — фазы и допустимые triggers, рискованные доменные гарантии, особенности окружения/CI, проверочные исключения.
- **tests/README.md**: карта каталогов, точные команды и технические prerequisites; не вторая политика.
- **Правило отсутствия дублирования:** универсальное правило меняется только в каноне, локальное — только у проекта. При противоречии сначала выясни владельца правила и синхронизируй источники; не копируй формулировки «для надёжности».
- **Progressive disclosure:** агент читает корневую точку входа всегда, локальные правила — когда задействованы тесты или решение о проверках, полный стандарт — когда нужно понять/изменить универсальный принцип. Объём загруженных инструкций должен соответствовать задаче.

## Источники и смежные стандарты

- [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html): проверять на максимально низком достаточном уровне.
- [Test Pyramid](https://martinfowler.com/bliki/TestPyramid.html): дорогие широкие UI-тесты склонны к хрупкости и задержкам.
- [GitHub Actions manual triggers](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow): workflow_dispatch.
- [DETai Release Fixation Standard](./release-fixation-standard.md): проверка релизного exact SHA — отдельный этап, а не каждое локальное изменение.
- [Storytelling Test Suite Rationalization](https://team.detai-x.com/task-center/lists/bb1582fa-5527-5b5f-a886-49f01c609d5e/items/2d92c61d-4435-5248-a579-8f9dadbf723d): исходная рационализация и acceptance criteria.
