# Стандарт создания Telegram-ботов

**Функция:** `standard`. Универсальные правила разработки Telegram-ботов DETai независимо от реализации: Python/Aiogram, TypeScript/Node.js или другого поддерживаемого стека. Общие принципы [мозаичного подхода](../mosaic-approach.md) — независимость компонентов, постепенность изменений, заменяемость и согласованные границы.

## Один продукт — один исполняемый контракт

- **Одна кодовая база продукта может обслуживать несколько экземпляров бота**, например DEV и Production. Различия токенов, ожидаемых Telegram Bot ID, аудиторий и внешних систем задаются **профилями**, а не копированием обработчиков в два проекта.
- Логика Telegram обновлений делится по предмету: вход/маршрутизация → проверка допуска и прав → прикладной сервис → данные/внешний провайдер → ответ. Названия файлов и папок зависят от стека; `routers/` и `handlers.py` — лишь пример Aiogram, не универсальный договор.
- Общее для нескольких ботов можно вынести в повторно используемый модуль со стабильным контрактом. Но **глобальная Identity, продуктовая подписка, платежный ledger, бот и интерфейс** имеют разных владельцев; нельзя подменять их локальной копией правил.
- API, worker и Telegram-интерфейс одного продукта должны использовать один продуктовый источник policy, серверную авторизацию и общую семантику idempotency. Разные сервисы не получают права из текста кнопки или клиентского состояния.

## Конфигурация как часть архитектуры

**Канонический [стандарт декларативной конфигурации](configuration-standard.md)** обязателен для новых ботов и применяется при модернизации существующих:

- В `config/` — действующие JSON/TOML для **несекретных** профилей, режимов и именованных списков с локальным README.
- Реальные Telegram-токены, ключи API/Commerce/AI и SQL credentials — **только в защищённом файле секретов вне отслеживаемого Git**; в репозитории только шаблон с заполнителями. Одного файла секретов на окружение продукта достаточно как физического источника, если учтены полномочия процессов.
- Приложение валидирует конфигурацию, не допускает незаметного перехода в публичный режим и сверяет `getMe().id` до запуска polling или модификации webhook.
- Сам факт размещения `bots.json` рядом с кодом не означает, что он используется. Поддерживать одновременно неиспользуемый JSON и действующие дубли в ENV запрещено.

## Handler, Policy и Service — разные обязанности

- Handler получает Telegram update, проверяет минимальную структуру, выбирает обработчик и отвечает пользователю. Он **не** назначает продуктовые права и **не** принимает платежное подтверждение на основании callback.
- Policy проверяет фактические полномочия, ограничения и контекст, применяя [общие правила Policy Layer](policy-layer.md). Rollout admission, тариф и административная роль продукта — независимые решения.
- Service выполняет сценарий и сохраняет изменяемые данные в серверном хранилище, а не в релизном Git или непроверенном локальном файле.
- Короткие действия остаются в обработчике; длительные и внешние задания используют durable очередь/worker с состояниями `pending/running/succeeded/failed/uncertain` или эквивалентом. Неизвестный результат Telegram/API/провайдера не разрешает слепой повтор денежной или пользовательской операции.

## Telegram UX и языки

- Inline-кнопки, ReplyKeyboard, deep links, команды и уведомления имеют **разные** механизмы получения события. Нельзя обещать callback-модальное окно от кнопки, которая присылает текст; удаление сообщений должно учитывать историю результата и пользовательскую навигацию.
- Пользовательские тексты и сценарии локализуются централизованно. [Язык и цель при переходе между ботами](language-handover.md) — отдельный контракт, не доказательство Identity и не тарифное право.
- Секреты, текст личных сообщений, токены, платежные payload и данные других пользователей не должны попадать в диагностические exports. Системный journal, SQL-факты, наблюдение UX и инциденты отличаются по назначению; ретенция — явно заданная политика.
- События обновлений/отправок с неопределённым исходом должны быть доступны оператору для безопасной reconciliation, а не автоматически повторяться до «успеха».

## Развёртывание и сопровождение

- `systemd`, контейнер или другой launcher выбирает разрешённый **профиль** и приватный файл секретов, а не хранит вторую копию бизнес-конфигурации. Путь к unit-файлам определяется owning repository и его release process; единой Python-папки `axiom/systemd_units/system` для всех ботов нет.
- Реальные токены, каталоги и правила доступа проверяются отдельно для каждого окружения. Merge в Git сам по себе **не** меняет работающий сервис или SQL и не включает новые платежи.
- При обновлении контракта меняются код и его ближайший README, тесты подтверждают целевую границу. Общая архитектура не пересказывается в каждом репозитории: на неё ставится ссылка. [Шаблон README бота](telegram-bot-readme.md) служит навигатором, **не** планом работ или журналом инцидентов.

### Языковые примеры, не нормативные директории

| Python / Aiogram | TypeScript / Node.js | Общее требование |
| --- | --- | --- |
| `routers/`, `handlers.py`, `states/` | `src/bot/`, `handlers.ts`, отдельный state store | Разделение UI и прикладной логики |
| `asyncio`, внешняя очередь при длительной работе | `async/await`, worker и durable SQL queue | Не блокировать обработчик, сохранять исход операции |
| TOML/JSON + проверенный parser | JSON + schema validator | Один реально читаемый несекретный конфиг |
| Приватный `secrets.env` | Приватный `secrets.env` | Нет токенов внутри versioned config |

Конкретные модули, FSM, очередь, версии SDK, шрифты и UI могут различаться: стандарт **не** обязывает все Telegram-боты применять одну Python-библиотеку, Redis или файловую структуру.
