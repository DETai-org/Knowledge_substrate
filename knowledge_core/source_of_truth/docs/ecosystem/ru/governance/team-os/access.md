# Team OS — роли, права и возможности

О заполнении профиля, публикации на сайте и подписи автора читай в
[руководстве по публичному профилю](public-profile.md).

[← Team OS — governance и модель вклада](../team-os.md)

Здесь собраны возможности каждой роли. Этот документ открывается из блока
**«Доступ и права»** в профиле участника. Роль описывает полномочия в Team OS;
профессия, вклад, репутация и экономические права определяются отдельно.

**Команда** — организационный контур DETai в Team OS. **Scope** — рабочая область
с определённым назначением и ответственностью: Infrastructure, Management Layer,
Onboarding, Projects или Tools. Например, владелец Onboarding отвечает за устройство
области включения новых участников, администратор помогает её сопровождать.
Ответственность оформляется явной ролью; название Scope никого не назначает.
**Проект** — направление внутри Scope: обычный наследует его доступ, закрытый имеет
отдельный состав участников с правом читать или редактировать.

Роль команды и роль Scope задаются независимо. Один человек может быть Member
команды, Admin в Infrastructure и Viewer в Management Layer. Admin идёт после Owner
по административным полномочиям, но эта роль не заменяет доступ к конкретной области.

| Роль | На уровне команды | Внутри Scope |
| --- | --- | --- |
| Owner | Организационные роли и доступы | Работа и управление областью |
| Admin | Приглашения и управление доступом в администрируемых областях | Работа и управление уровнями Admin/Editor/Viewer |
| Member | Участие без организационного администрирования | В API `member` соответствует Editor |
| Editor | Отдельной организационной роли нет | Создание и изменение рабочих записей |
| Viewer | Отдельной организационной роли нет | Чтение рабочих данных |

Права Team OS сами по себе не выдают доступ в GitHub, на серверах, в других приложениях
или полномочия на финансовые решения. Закрытые проекты сохраняют отдельные границы
доступа. Чужое личное пространство не открывается административной ролью.
GPT использует права персонального подключения и разрешённые операции Core.

Настройка порядка дерева и записей описана ниже в возможностях соответствующих ролей.
Изменения реализованы в [Team OS PR #98](https://github.com/DETai-org/team-os/pull/98) и развёрнуты в production. При изменении прав необходимо сверять эту справку с Core и обновлять документ вместе с соответствующим контрактом.

## Personal и Team Workspace

Выпущено 14 октября 2026 года: [Team OS #105](https://github.com/DETai-org/team-os/pull/105)
и [корректирующий #106](https://github.com/DETai-org/team-os/pull/106).
Технические границы описаны в
[контракте Personal / Team Workspace](https://github.com/DETai-org/team-os/blob/main/docs/contracts/team-workspace.md).

**Мой рабочий стол** показывает назначенные человеку задачи и созданные им Notes /
WorkLogs. Участие в чужой сводке не делает её собственной. Focus, Principles,
Guidance, контрольные точки и раскладка остаются прежними личными моделями.
Завершённые задачи отбираются по completedAt, открытые — по сроку; бессрочные
не пропадают при выборе периода.

**Командная работа** показывает dashboard и общие каталоги Tasks, Notes и WorkLogs.
Любой действующий участник команды видит разрешённые организационные метаданные,
включая факт работы в закрытом проекте или Scope без собственного доступа:
название, расположение, автор, исполнители, даты, статус и приоритет.
Личные пространства, Home, ориентиры, тексты, история, вложения и credentials
в общий каталог не входят. Просмотр метаданных не выдаёт права открыть содержимое.
Custom Fields общекомандны только после отдельного разрешения Scope Owner/Admin
либо Organization Owner; новые поля по умолчанию закрыты для этого каталога.

В текущем выпуске «Зарегистрированные проекты» считает действующие Project Profiles.
В [планируемом Team OS #107](https://github.com/DETai-org/team-os/pull/107)
это исправляется: проектом считается только непосредственная Folder канонического
Scope Projects. Операционные регистрации в Onboarding, Infrastructure и Tools
сохраняют Tasks/Notes/WorkLogs, но не появляются в Project Access и счётчике портфеля.
Новая папка первого уровня Projects автоматически становится проектом; название
папки не служит признаком. Пока R&D находится на этом уровне, правило относится
и к ней; отдельное исключение по имени не вводится. Открытые задачи и проекты — состояние
сейчас; завершения, заметки и финальные сводки — показатели выбранного периода. Direct Project Access без Scope membership сохраняется.
Просмотр безопасного Scope Overview не открывает соседние рабочие объекты.

| Project Role | Содержимое и управление |
| --- | --- |
| Viewer | Читает содержимое при effective ACL, без изменений |
| Editor | Читает и изменяет разрешённые рабочие записи |
| Admin | Работает с записями и управляет участниками своего Restricted проекта |
| Owner | Максимальная проектная роль; не заменяет организационные полномочия |

Прежние read/edit переходят в Viewer/Editor. Inherited использует роли Scope;
сохранённые прямые назначения действуют только в Restricted. Смена режима
подтверждается отдельно и объясняет изменение аудитории. Никакой automatic
Projects Viewer не выдаётся.
Project Admin/Owner не получают Scope/Organization authority или доступ к чужому
личному пространству. Назначить, снять или заменить Project Owner могут только
Organization Owner/Scope Owner. Менять inherited/restricted могут Organization
Owner или Scope Owner/Admin. Org Admin без полномочий Scope не получает новый
проектный bypass. Вложенные restricted boundaries предков сохраняются.

Карточка и профиль участника отдельно показывают Scopes и Projects. Изменения
проекта сохраняются версионно с аудитом через единый Core ACL. Отзыв доступа
очищает открытую панель при повторной проверке; каждая операция Core проверяет
права независимо. Завершение членства закрывает также общий каталог.

В открытой Note доступен тот же блок parent/children и создания подзаметки,
что у Task. Создание требует edit ACL конкретного списка и write scope; Viewer
видит связи без права создания. WorkLogs остаются плоскими. Общий редактор
описания сохраняет авторство блоков: участник не перезаписывает текст другого
автора. «Открыть список» появляется только при переходе из обзора/подборки и
скрывается, когда исходный List уже открыт в центре.

MCP получает общекомандную сводку по явному запросу. Она не загружается
автоматически в Personal Home AI Context. OAuth write не делает Viewer Editor;
выдавать project grants через MCP по-прежнему нельзя. Неизвестные исторические
авторы и даты финализации не заменяются последним редактором или updatedAt.

## Owner — Владелец

### Owner команды {#team-owner}

**Управляет организационными ролями, может назначать администраторов и управлять
доступом к любому Scope. Смена или снятие Owner защищена дополнительными ограничениями.**

- Меняет организационные роли участников, назначает администраторов и владельцев команды.
- Управляет доступами к Scope; назначает и снимает Owner конкретного Scope.
- Приглашает участников.
- Завершает участие Admin или Member через «Удалить из команды». Очистка профиля,
  архив UUID и переназначение доступных открытых задач входят в этот поток.
- Настраивает общий порядок доступных Scopes и внутренних папок/списков,
  соблюдая доступ к элементам и право редактирования закрытых проектов.
- В своём личном пространстве работает с записями и управляет собственным деревом.
- Для обычной работы с Tasks, Notes и WorkLogs соблюдает права соответствующего
  Scope или проекта; административная роль не заменяет рабочий доступ.

Система сохраняет хотя бы одного активного Owner. Понижение собственной роли из
профиля защищено серверной проверкой. Владение командой не даёт доступа к чужому
личному пространству или к содержимому закрытого проекта без предусмотренного допуска.

Карандаш рядом со **Scopes** включает настройку порядка. До сохранения изменения
видит только редактор; **«Сохранить»** публикует общий порядок,
**«Отмена»** возвращает сохранённый. Переставлять можно только соседей одного родителя,
включая ветку целиком. Родитель, UUID, тип списка, ссылки и права сохраняются.
Переноса между папками/проектами в этой версии нет. Недоступные элементы не раскрываются
и не изменяются. Core сохраняет пакет атомарно и отклоняет конфликт одновременных
изменений; несохранённый порядок остаётся на экране. Другие открытые клиенты получают
общий порядок при обновлении дерева. Раскрытие/сворачивание каждый настраивает для себя.

### Owner Scope {#scope-owner}

**Полный рабочий доступ и управление участниками Scope. Назначить или снять
владельца Scope может только организационный Owner.**

- Работает с доступными задачами, заметками и рабочими сводками области.
- Настраивает общий порядок записей в разрешённых для редактирования List.
- Управляет доступами участников этой области в пределах серверных ограничений.
- Настраивает порядок папок и списков среди соседей своей области, с теми же
  сохранением и отменой; в закрытом проекте требуется право редактирования.
- Отвечает за организацию и назначение области.

Полномочия ограничены Scope и границами закрытых проектов. Owner Scope не становится
Owner команды и не меняет организационные роли или владельцев Scope.

## Admin — Администратор

### Admin команды {#team-admin}

**Приглашает участников и управляет доступом в тех Scope, где сам имеет роль Owner
или Admin. Не может назначать организационного Owner или менять его права.**

- Приглашает участников.
- Завершает участие Member. При завершении участия может переназначить или снять
  исполнителя только в открытых задачах, которые сам вправе редактировать;
  история, другие исполнители и недоступные/завершённые задачи сохраняются.
- Управляет уровнями Admin, Editor и Viewer в Scope, где сам является Owner или Admin.
- Настраивает общий порядок доступных Scopes.
- Настраивает внутренний порядок папок/списков только в своих администрируемых Scope,
  с доступом к затрагиваемым элементам и правом редактирования закрытого проекта.
- Работает с разрешёнными записями согласно своим рабочим доступам.
- Управляет собственными записями и порядком личного пространства.

Изменение организационных ролей и назначение/снятие Owner Scope остаётся полномочием
Owner команды. Admin команды не получает автоматически полный доступ ко всем областям.
Настройка дерева использует тот же карандаш, перестановки соседей, сохранение и отмену,
что описаны у Owner. Раскрытие/сворачивание веток остаётся личным.

### Admin Scope {#scope-admin}

**Может работать с содержимым Scope и выдавать или ограничивать уровни Admin,
Editor и Viewer другим участникам этого Scope.**

- Создаёт и изменяет разрешённые рабочие записи области.
- Настраивает общий порядок записей в разрешённых для редактирования List.
- Управляет уровнями Admin, Editor и Viewer её участников.
- Настраивает порядок соседних папок и списков области с доступом к затрагиваемым
  элементам; в закрытом проекте требуется право редактирования.

Не меняет владельцев Scope и организационные роли. Правила закрытого проекта
сохраняются. Роль Admin Scope не назначает человека Admin команды.

## Member — Участник {#team-member}

**Рабочие возможности определяются доступом к конкретным Scope. Роль участника
не означает Viewer: в каждом Scope отдельно задаётся свой уровень.**

- Работает с доступными Tasks, Notes и WorkLogs в соответствии с уровнем Scope
  и правами проекта.
- Настраивает раскрытие/сворачивание веток для себя.
- Заполняет свой командный и публичный профиль. Отдельно подтверждает
  участие в блоге и публикацию расширенной страницы. Авторский флажок требует окна
  подтверждения в обе стороны и сохранения формы; менеджер не даёт согласие за него.
  Имя, короткое описание и фото могут быть опубликованы для подписи автора;
  расширенная биография и контакты — только по отдельному согласию.
- В собственном личном пространстве работает с записями и настраивает порядок дерева.
- Если отдельно назначен Owner/Admin Scope, получает административные возможности
  этой области, описанные выше.

После принятия приглашения подтверждённый DETai Account с активным членством
автоматически получает доступ к Home и личному пространству. Отдельное ручное
включение аккаунта не требуется. Завершение членства закрывает
Home и личное на следующем запросе, сохраняя личные данные и DETai Account.
Доступ к командным Scope и проектам по-прежнему определяется отдельными ролями.

При завершении участия Team OS очищает текущий профиль команды и оставляет минимальную
архивную запись UUID/дата. Старые статьи и Person/Author IDs сохраняются. Публичная
карточка исчезает после публикационного PR и production deployment сайта; существовавший
URL становится минимальным архивом. Account, личные данные, история задач и backups
не удаляются этой операцией. Технические дубли сначала требуют явного сопоставления.

Без соответствующей отдельной роли не управляет доступами, приглашениями,
организационными ролями или общим порядком Scopes. Личное владение сохраняется
независимо от членства в команде; административные роли других людей его не заменяют.
Перенос между личным и командным контуром здесь не разрешается.

## Профиль и AI

В Web/Core/MCP выпущены изменения по [политике данных участника](profile-data-and-visibility.md):
индивидуальный выбор публичных биографии, интересов, образования, вклада и каждой
социальной ссылки; фото как обязательный минимум новой полной Team Profile;
приватное первое сохранение Principles с независимым useInAi; компактный контекст
коллеги в MCP и дополнительное чтение только по ACL и явному контексту запроса.
Старые согласия/аудитории сохраняются, новое поле вклада не публикуется автоматически.
Механизмы internal access, AI, Team Profile и Personal Profile независимы.
Personal Profile остаётся ранней beta/noindex, без обещанной синхронизации.
Согласованная реализация: [Team OS #105](https://github.com/DETai-org/team-os/pull/105).

В интерфейсе применяется единое английское отображение ролей:
Organization — **Owner, Admin, Member**; Scope — **Owner, Admin, Editor, Viewer**;
отсутствие grant — **No access**. API идентификатор Scope `member` сохраняется и
отображается как Editor. Это смена терминов, без изменения прав и сохранённых
назначений. Ниже русские пояснения описывают смысл уровней.

Renderer и JSON-LD: [Sites Draft #608](https://github.com/DETai-org/sites/pull/608).

Командное публичное имя и контакты хранятся в отдельной
Team projection; публикация не перезаписывает глобальные Person name/sameAs/URL.
Собственное SEO-описание получает отдельное разрешение и остаётся публичным
независимо от скрытых секций; без разрешения используется описание деятельности.
Новая полная страница требует собственной проверенной Identity photo projection.
Migration 0026 сохраняет уже опубликованные фотографии и SEO без новых неявных
разрешений. Внутренние карточки показывают заполненные соцсети только действующим
участникам команды; публичный сайт получает только выбранные ссылки.


## Editor — Редактор {#scope-editor}


**Может создавать и изменять рабочие сущности в Scope, но не управляет доступом
других участников.**

- Создаёт и изменяет разрешённые Tasks, Notes и WorkLogs.
- Настраивает общий порядок соседних записей внутри разрешённого List.
- У задач использует назначения и workflow; у Notes и WorkLogs сохраняет авторство.
  Завершение WorkLog не закрывает задачи.
- Настраивает раскрытие/сворачивание веток для себя.
- Сохраняет возможности владельца своего личного пространства, включая его порядок.

Не управляет доступами участников и общим порядком дерева области. Правила закрытых
проектов проверяются отдельно; право редактировать проект не означает право менять
его доступы. В API этот уровень называется `member`, в интерфейсе — **«Редактор»**.
Это соответствие существующих названий, а не дополнительная роль.

Кнопка со стрелками вверх/вниз рядом с настройками List включает режим порядка Tasks,
Notes или WorkLogs. Ручка переносит запись между соседями одного родителя; стрелки
перемещают на один шаг. В этом режиме добавление вложенных записей скрыто.
«Сохранить» публикует общий для всех участников List порядок и закрывает режим,
«Отмена» отбрасывает черновик. До сохранения изменения видит только редактор.
Core сохраняет пакет атомарно: при конфликте версий черновик остаётся на экране.
Другие открытые клиенты получают порядок при следующем обновлении List.
Родители, содержимое, авторство, workflow и рабочая дата сохраняются.

## Viewer — Наблюдатель {#scope-viewer}

**Может просматривать доступные рабочие данные Scope, но не менять их
и не управлять участниками.**

- Читает разрешённые задачи, заметки и рабочие сводки.
- Видит разрешённую часть общего порядка дерева и сохранённый порядок записей List.
- Настраивает раскрытие/сворачивание веток для себя.
- Сохраняет возможности владельца своего личного пространства; ограничение Viewer
  относится к назначенному Scope.

Не создаёт и не изменяет записи области, не меняет доступы и общий порядок дерева.
Роль Viewer Scope не открывает недоступные проекты. В закрытом проекте действуют
отдельно назначенные права его участника.

## Преобразование Folder ↔ Scope

В [Team OS #105](https://github.com/DETai-org/team-os/pull/105) выпущено
контекстное действие «Преобразовать в scope» / «Преобразовать в папку».

- Доступно только действующим **Organization Owner и Admin**, через Web session.
  Scope Owner/Admin и Project Owner/Admin сами по себе этого права не дают.
  Требуется право изменения исходной ветки; закрытый недоступный потомок блокирует
  операцию. Для обратного преобразования нужен доступ на изменение целевого Scope.
- Folder становится отдельным Scope в конце дерева. Его ID, ссылки, вложенные
  списки, Tasks, Notes, WorkLogs и проектная навигация сохраняются. Начальное
  Scope membership получает только инициатор; после сохранения он может сразу
  открыть «Настроить доступ» и назначить роли участникам.
- Эффективные права закрытых вложенных проектов не расширяются при снятии
  родительской границы. Неактивные grants не превращаются в новый доступ.
- Scope становится Folder в конце выбранного Scope. Его прежняя аудитория
  сохраняется как restricted Project Access. Участники целевого Scope не получают
  содержимое автоматически. Прежние Scope memberships и настройки удаляются;
  ожидающие приглашения больше не выдают роль в преобразованном Scope.
- Конвертация выполняется одной транзакцией с проверкой версии. Конфликт,
  отозванное право или недоступная ветка не оставляют частично перенесённых данных.
  Личные пространства и List в это действие не входят; OAuth/MCP не получают
  полномочия преобразования.

## Перенос Folder между Scopes — планируется

В [Team OS #107](https://github.com/DETai-org/team-os/pull/107) добавляется перенос
полной папки через общий режим настройки дерева: перетащить Folder на строку
другого Scope, проверить направление и нажать «Сохранить».

- Только **Organization Owner/Admin** через Web session, с правом изменения
  исходной ветки и целевого Scope. Роли Scope/Project отдельно и OAuth/MCP
  не дают этого полномочия. Личные пространства не затрагиваются.
- Folder меняет реального родителя; её ID, ссылки, вложенные Lists, Tasks,
  Notes, WorkLogs, авторы, рабочие даты и маршруты сохраняются. Используемые
  поля, типы, метки и изображения переносятся вместе со своей веткой.
- Прежняя effective аудитория сохраняется как Restricted boundary папки.
  Участники целевого Scope автоматически не получают содержимое. Вложенные
  закрытые назначения не расширяются после снятия старого родителя.
  Закрытый потомок без edit-доступа блокирует перенос, включая архивную ветку.
- Изменение структуры и порядка сохраняется одной SQL-транзакцией с исходными
  версиями и audit. При конфликте сохраняется черновик на экране; частичного
  переноса нет. Lists между папками в этом режиме не переносятся.
- Перенос на первый уровень Projects включает папку в портфель; перенос в
  обычный Scope выводит её из портфеля. Рабочая регистрация и исторические ACL
  сохраняются, даже когда папка больше не показывается в Project Access.

Выбор Task, Note или WorkLog внутри одного List меняет только правую панель
и адрес записи. Центральный список сохраняет прокрутку, фильтры и ширины столбцов;
Back/Forward восстанавливает выбор. Home, «Мои задачи», командный каталог и
«Личное» используют тот же принцип. Загрузка разрешённого текста справа
не означает повторную загрузку списка.
