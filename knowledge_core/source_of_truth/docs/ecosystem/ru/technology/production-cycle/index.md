# Производственный цикл

Производственный цикл U.L.I. описывает dev-этап создания цифрового проекта или его следующей версии: от идеи и проектного намерения до реализации кодовой части, проверки, фиксации версии и связанной технической документации.

Короткая формула цикла:

```text
мысль/идея -> план проекта -> Epic Issue -> Work Package -> код / результат -> версия -> документационная обвязка -> новый смысл
```

## Граница производственного цикла

В этом цикле команда Улья создаёт и развивает **кодовую часть цифрового решения**. Готовый к публичному выпуску результат через [Management Layer](../../management-layer/index.md) передаётся в [Brand & Communications](../../brand-and-communications/index.md), где продолжаются работа с брендом, публичным представлением и аудиторией продукта.

В технологическом контуре действует правило:

> Один репозиторий соответствует одному проекту.

Проект может создавать внешнюю или внутреннюю ценность. Он может стать пользовательским продуктом, а может остаться инфраструктурой, внутренним инструментом, медиа-проектом или технической capability. В любом случае проект должен усиливать хотя бы один [ресурс экосистемы](../../management-layer/ecosystem-resources.md).

Для начала разработки достаточно инициативы участника, согласованной с миссией, ценностями и принципами DETai.

## Модель работы внутри цикла

Этапы **Work Model Planning** и **Implementation** опираются на модель работы: проектное намерение превращается в организованную работу и поставляемый результат. Её состав задают три документа:

| Документ | Назначение |
| --- | --- |
| [Epic Issue Contract](epic-issue-contract.md) | Обязательная структура верхнеуровневого блока смысла, границ работы и критериев завершения |
| [Work Package Contract](work-package-contract.md) | Контракт поставляемого фрагмента работы: результат, проверка и связь с branch и PR |
| [Work Model](work-model.md) | Общий процесс от Epic Issue через Work Package до проверяемого результата |

Для знакомства с моделью сначала прочитай **Work Model**; при оформлении конкретного Epic Issue или Work Package используй соответствующий контракт. Подробная механика Acceptance Tasks, Implementation Steps, PR и завершения работы описана в Work Model. Этот индекс показывает её место в цикле разработки U.L.I.

## 1. Project Intent

На первом этапе появляется мысль, наблюдение или возможность, которая постепенно оформляется в проектное намерение.

Здесь важно понять:

- что именно должно измениться;
- зачем это изменение нужно;
- какой новый смысл или ресурс оно может дать экосистеме;
- готова ли мысль стать проектом или пока должна остаться в пространстве наблюдений.

Если идея ещё не созрела, она фиксируется как импульс. Для этого в нашей системе есть место, оно называется "🧠 Еще мысль", это материал/хаб для будущего развития. Если из неё уже сформировался вектор, он может перейти в Epic Issue.

Смысловую методологию этого перехода описывает документ [Методология проектного цикла DETai](project-cycle-methodology.md).

## 2. Work Model Planning

На втором этапе проектное намерение переводится в четкий план.

Здесь формируются:

- Epic Issue как блок смысла и навигации;
- Sub-Issue / Work Package как поставляемые фрагменты результата;
- Acceptance Tasks как проверяемые результаты;
- критерии завершения и связи с будущим PR.

Общую механику планирования описывает [Work Model](work-model.md), а обязательные поля Epic Issue и Work Package задают соответствующие контракты.

Как дополнительный связанный материал к этому этапу см. [Совместное планирование человека и агента в Work Model Planning](../uli/collaborative-planning.md) — документ о распределении high-level и low-level ролей между человеком и агентом.

## 3. Implementation

На третьем этапе Work Package выполняется.

Типичная форма выполнения:

```text
Work Package -> branch -> PR -> проверка -> merge
```

На этом уровне Codex или другой исполнитель работает внутри заданного Epic Issue, выполняет Sub-Issue / Work Package / checklist, фиксирует важные решения и доводит результат до проверяемого состояния.

Этот этап также регулируется Work Model: именно там описаны роли Epic Issue, Work Package, Acceptance Tasks, Implementation Steps, PR и финальной проверки.

## 4. Release Fixation

Release Fixation отвечает за момент, когда результат работы перестаёт быть набором изменений и становится зафиксированным состоянием проекта, репозитория или документационной системы.

На этом этапе уточняется:

- какая версия или состояние завершены;
- какие PR, решения и документы входят в итог;
- что должно быть отражено в changelog, release notes или release summary.

Дополнительно определяется тип достигнутого состояния:

- внутренняя или предварительная версия проекта `v0.x`;
- стабильная версия внутреннего проекта или capability;
- выпуск или обновление сознательно оформленного внутреннего продукта;
- публичный `v1.0` проекта, готового перейти из пилота в публичный продукт;
- новая публичная версия уже существующего продукта.

Стабильная `v1.0` фиксирует готовность к устойчивой внутренней работе или публичной ответственности. Для перехода в продукт нужны ценностная значимость для определённой аудитории, работающий способ доступа, владелец поддержки и показатели наблюдения. Для внешнего продукта доступ публичный; для сознательно оформленного внутреннего продукта он может быть ограничен установленной аудиторией. Версия сама по себе не присваивает продуктовый статус.

Если проект независимо выпускает несколько компонентов, для каждого выпуска фиксируются компонент, версия, точный commit SHA, состав изменений и применимая проверка по локальному стандарту. Состояние исходников, опубликованного артефакта и production-развёртывания различается; версия пакета не доказывает доставку пользователю.

Этот этап описан отдельным стандартом [Release Fixation Standard](../uli/standards/release-fixation-standard.md) и не смешивается с Work Model.

## 5. Documentation Architecture

На пятом этапе результат цикла связывается с Knowledge Substrate и другими документальными слоями.

Здесь определяется:

- какие документы нужно обновить;
- какие новые документы нужно создать;
- какие старые документы стали устаревшими;
- какие статусы и версии должны измениться;
- какие рабочие материалы связать со списком заметок «Новые версии документов» в Management Layer; задачи исполнения ведутся отдельно в соответствующих Task Lists.

Если релиз создаёт или обновляет продукт, Documentation Architecture также проверяет:

- канонический продуктовый узел и его текущую версию;
- ценностную значимость, аудиторию и обещанный результат;
- ограничения, поддержку, источники наблюдения и условия доступа;
- для внешнего представления — статус и описание на сайте, два базовых GEO-вопроса, SEO/GEO metadata и structured data;
- для внутреннего продукта — доступный его аудитории маршрут использования и документации.

Канонические определения и правила обновляются в Knowledge Substrate, контракты реализации и release evidence — в owning repository, а назначения, рабочие маршруты и паспортные ссылки — в Team OS. Изменение документации не подтверждает автоматически применение миграции, развёртывание Web или установку новой версии Plugin.

На этом этапе производственный цикл не исправляет все представления самостоятельно. Он передаёт Management Layer сигнал о выпуске и перечень изменившихся канонических объектов. Management определяет затронутые домены: Product–Market подтверждает ценность, Brand & Communications и владельцы каналов обновляют публичные проекции, а профессиональные и правовые проверки выполняются по предмету изменения.

Изменившийся продуктовый смысл не считается синхронизированным, пока Management Layer не подтвердил, что связанные представления обновлены либо явно отмечены как неприменимые.

Этот этап закрывает цикл: результат становится частью знания экосистемы и может породить новые мысли, наблюдения и будущие проектные намерения.

## Связь с продуктовым циклом

[Продуктовый цикл Product–Market](../../brand-and-communications/product-market-cycle.md) описывает пилот, публичный запуск и сопровождение пользователей в Brand & Communications. Аналитика и обратная связь обсуждаются командой продукта и превращаются в идеи улучшений; принятые изменения начинают новый производственный цикл U.L.I. После релиза обновлённая версия возвращается пользователям, а Brand & Communications сообщает об изменениях.

Производственный и продуктовый циклы идут параллельно и соединяются в точках публичного релиза или сознательного оформления внутреннего продукта.

| Состояние | U.L.I. / производственный цикл | Product–Market / продуктовый цикл |
|---|---|---|
| Мысль и ранняя инициатива | Даёт свободно развить идею | Не обязан подключаться |
| Проект и `v0.x` | Планирует, реализует и фиксирует версии | Может консультировать по запросу, но не создаёт обязательный gate |
| Подготовка публичного `v1.0` | Готовит стабильный релиз, передаёт Management сигнал об изменении и готовит deployment | Совместно с командой пилота формулирует ценностную значимость, аудиторию, доступ и показатели |
| Внутренний продукт | Фиксирует стабильное состояние и доставку установленной аудитории | Вместе с владельцем подтверждает аудиторию, результат, поддержку и наблюдение; публичные представления проверяются по применимости |
| Публичный продукт | Поддерживает production-состояние | Наблюдает использование, ресурсный вклад, доход и обратную связь |
| Следующая версия | Развивает проект в новом dev-цикле | Передаёт наблюдения и проверяет, изменилась ли ценность продукта |

В проектах с ветками `production` и `dev` поддерживаемая версия остаётся в production-контуре, пока следующая версия развивается в `dev`. После Release Fixation следующего major-релиза соответствующий owning runtime обновляет доставляемое состояние; Product–Market и владелец подтверждают ценность и показатели; Management Layer координирует синхронизацию. Для внешних продуктов Platform DETai доставку обеспечивает платформа, а Brand & Communications и владельцы затронутых каналов обновляют публичные представления.

Подробная продуктовая сторона интерфейса описана в [модели продуктового объекта](../../brand-and-communications/product-market/product-object-model.md), [стандарте ценностного предложения](../../brand-and-communications/product-market/value-proposition-standard.md) и [рыночном и портфельном цикле](../../brand-and-communications/product-market/market-operations.md). Явная последовательность передачи ответственности дана в [интерфейсе производственного и продуктового циклов](../index.md#эстафета-публичного-релиза).

## Роли и skills

Производственный цикл может поддерживаться разными ролями и Codex skills.

На уровне Project Intent skill может выполнять роль фасилитатора и сверять идею с тем, какой ресурс эта идея может принести и в каком из эшелонов он может быть будущий проект.

На уровне Work Model Planning и Implementation ключевым становится агент, который умеет работать внутри Epic Issue / Work Package, удерживать scope, выполнять checklist и готовить PR.

Отдельную логику совместной planning-коммуникации между человеком и агентом раскрывает документ [Совместное планирование человека и агента в Work Model Planning](../uli/collaborative-planning.md).

## Граница документа

Этот документ отвечает за карту цикла и распределение ответственности между этапами.

Он не должен подробно описывать:

- внутреннюю механику Acceptance Tasks и PR;
- правила повышения версий документов;
- конкретный формат release notes;
- политику metadata;
- правила публикации Knowledge Substrate.

Эти темы должны жить в соответствующих стандартах и процессных документах, а производственный цикл должен связывать их в одну понятную траекторию.
