# Документационная архитектура U.L.I.

**U.L.I. Document System — документация среды цифровой разработки и её проектов.**
Она помогает человеку и AI-агенту понимать замысел, устройство решения, рабочие
правила, способ реализации и проверку результата.

Улей — рабочая среда, которая использует общие правила экосистемы и применяет их
в локальном контексте разработки. В этой области он определяет прикладную
типологию документов: какие функции нужны разработке, как они используются
и где находятся соответствующие материалы.

[Обзор правил документации](index.md) связывает эту практику с документацией
сайта MkDocs. Общий словарь находится в [функциях документов](documentation-functions.md),
а описание metadata — в [политике metadata](metadata-policy.md). Здесь раскрыто
их применение в разработке.

## Уровни действия и смысловые группы

Документ среды действует на разработку в Улье в пределах явно обозначенной
области: например, общий стандарт или объяснение производственного цикла.
Документ проекта относится к конкретному решению или репозиторию: локальной
архитектуре, настройке, инструкции или принятому техническому решению.

Содержание удобно рассматривать через три группы: **смысловые основания**,
**устройство и логику**, **рабочие правила**. Это способы ориентироваться
в документации; они не требуют трёх одинаковых папок в каждом проекте
или отдельной группы Philosophy в меню сайта.

## Типы документов в U.L.I. и их локальное применение

Названия в таблице обозначают функции документов. Они не задают типы продуктов,
финансовых записей или объектов других направлений экосистемы.

| Функция | Применение в разработке | Уровень действия | Типичное размещение |
|---|---|---|---|
| `index`, `guide` | вход в документацию среды или проекта, маршруты к нужным материалам; README может выполнять эту функцию | среда / проект | MkDocs для среды, README или docs/ проекта для локального входа |
| `philosophy`, `principle` | основания совместной работы людей и AI, устойчивые инженерные установки | среда / проект | объяснения и принципы в MkDocs либо документация проекта |
| `explanation` | замысел, архитектура, связи компонентов и причины выбранного устройства | среда / проект | MkDocs или репозиторий соответствующего проекта |
| `standard`, `policy` | форма рабочих артефактов, правила разработки и изменения результата | среда / проект | общие правила в MkDocs, локальные правила в репозитории |
| `reference` | параметры, команды, интерфейсы, конфигурация и другие точные сведения | проект | документация и поддерживаемая справка проекта |
| `tutorial`, `how-to` | первое освоение проекта или выполнение конкретной задачи | проект / обучение | репозиторий проекта; общий маршрут участника может ссылаться на материал через Onboarding |
| `runbook` | повторяемая операция, выпуск, восстановление или разбор инцидента | проект / эксплуатация | документация ответственной команды с подходящим доступом |
| `decision-record` | контекст и последствия технического решения; ADR — проектное применение этой функции | проект | каталог решений в репозитории |
| `register` | управляемый перечень компонентов, решений или иных объектов разработки | среда / проект | у владельца перечня по его правилам обновления |
| `brief`, `note`, `log-summary` | постановка ограниченной работы, рабочая мысль, датированный итог | проект / работа | в рабочей системе или проектной документации по контракту соответствующего артефакта |

Указанное размещение — ориентир. Функция выбирается по назначению текста;
источник определяется тем, кто поддерживает его актуальность и вместе с чем
он должен изменяться.

## Документация рядом с реализацией

Локальное объяснение, инструкция, стандарт или ADR хранится в репозитории проекта,
когда зависит от его устройства и должно изменяться вместе с кодом. Проект может
уточнять правила среды для своей области; применимость и согласованные исключения
должны быть явными. Из одной вложенности папок нормативная сила не выводится.

Для metadata используется [контракт проекта](metadata-schema-registry.md#contract-ecosystem)
или принятый им профиль общих полей. Это не требование добавлять полный
экосистемный YAML в каждый README, ADR или файл справки. Функция, актуальная
версия и ответственный должны быть понятны в форме, принятой в проекте.

Если tutorial или how-to используется как встроенная помощь продукта, интерфейс
может показывать текст из того же источника. Это помогает обновлять инструкцию
вместе с функцией и сохранять соответствие между документацией и поведением
продукта. Onboarding остаётся каналом обучения и может вести к такой инструкции.

## Связь с производственным циклом

Документы сопровождают [dev-этап создания версии](../production-cycle/index.md):
замысел и план, реализацию, проверку и фиксацию результата. Epic Issue и Work Package
используют собственные [рабочие контракты](../production-cycle/work-model.md);
эта таблица функций не заменяет их поля и критерии готовности.

Итоги версии и изменения ресурсов фиксируются по правилам
[Release Fixation](../production-cycle/release-fixation-standard.md). Локальный
каталог отчётов проекта, если он используется, хранит результат фиксации версии.
Дневная история работы сохраняется в разрешённом WorkLog-контуре
[Team OS](../../management-layer/team-os/plugin.md); Task, Note и WorkLog
имеют собственные контракты и права доступа.

## Изменения и публикация

Версия документа меняется по [правилам версионности](../versioning.md).
Готовность кода и актуальность описания проверяются отдельно: новый текст
сам по себе не подтверждает реализацию возможности.

При публикации в MkDocs применяется
[правило публичности](metadata-policy.md#публичность-mkdocs).
Локальные инструкции с ограниченным доступом остаются у владельца проекта;
публичная страница описывает устойчивую модель и доступные читателю сведения.
