# Версионность: процесс и стандарт

Версионность фиксирует состояние системы во времени: какой этап развития достигнут, какая редакция действует и где готовится следующая. Этот документ объединяет смысл версионности, форматы номеров и правила пересмотра документов DET / DETai.

Версия может описывать проект, документ, правило, процесс или смысловую рамку. Её изменение означает признание нового устойчивого состояния. Версия повышается осознанно по решению ответственных, после завершения логического этапа; коммит, закрытая задача, deployment или прошедшее время сами по себе её не повышают.

## Версии проектов и SemVer

В классическом Semantic Versioning номер имеет три части: `MAJOR.MINOR.PATCH`, например `1.4.2`. В DET / DETai это отправная точка, а не универсальный формат для любого объекта.

Для проектов U.L.I. действует собственная смысловая модель и правила выпуска компонентов. Они описаны в [версировании проектов U.L.I.](uli/standards/project-versioning.md). Проектная версия фиксирует состояние решения; версия документа — редакцию знания или правила о нём. Release проекта не определяет статус описывающего его документа.

## Номера версий документов

Для документов типов `explanation`, `standard`, `policy`, `tutorial`, `guide`, `how-to` и `reference` используется одноуровневая модель: `v1`, `v2`, `v3`.

Каждый новый номер обозначает содержательную редакцию. Исправления опечаток, форматирования и ссылок не требуют повышения версии, если смысл остаётся прежним. При смысловом изменении обновляются `descriptive.version`, даты и применимые связи; стабильный ID документа сохраняется.

Для философских документов с `layer: philosophy` и governance-документов, излагающих принципы, концепцию или доктрину, может применяться edition: `1st-edition`, `2nd-edition`, `3rd-edition`.

## Статус, нормативная сила и редакционная работа

| Что фиксируется | Где хранится | Значение |
|---|---|---|
| Жизненный цикл и версия документа | YAML metadata в Knowledge Substrate | `descriptive.status: active` — действующая редакция; `draft` — рабочий текст для review |
| Каноническая и нормативная сила | `governance.canonicality` | Определяется отдельным решением; статус `active` сам по себе не делает рабочую модель обязательной нормой |
| Подготовка и рассмотрение новой редакции | Ветка, PR и рабочие записи Team OS | Исходное состояние, новая редакция, review, готовность к публикации и опубликованный результат |

Остальные значения статусов определяет [политика metadata](../knowledge/metadata-policy.md). Статус Task, Note или PR не присваивает документу нормативную силу. Публикация файла также не переводит `draft/working` в `active/canonical` автоматически.

Работа над новой редакцией не отменяет опубликованную. Пока идёт review, действующая версия остаётся исходным состоянием; её не требуется переводить в `draft` только из-за появления PR.

## Как подготовить и опубликовать новую редакцию

1. Найти канонический Markdown-файл, проверить владельца, назначение и границы документа.
2. Зафиксировать исходное состояние ссылкой на файл и неизменяемый commit SHA. Git хранит версии; полнотекстовый дубликат в task-системе не обязателен.
3. Подготовить новую редакцию в рабочей ветке по правилам репозитория. Для документов экосистемы применяется маршрут `docs/ecosystem → main`.
4. При смысловом изменении повысить номер версии, обновить дату редакции и документальные связи, сохранив stable ID.
5. Провести содержательный review; проверить metadata, прямые ссылки, навигацию, публичность и сборку MkDocs.
6. Опубликовать редакцию через принятый PR-процесс и отдельно подтвердить изменения статуса или нормативной силы, если они требуются.
7. Связать рабочие материалы и итог с PR и опубликованной версией. Предыдущая редакция остаётся доступной в Git history.

В metadata содержательной версии указываются:

```yaml
descriptive:
  version: v<N>
  status: <подтверждённый статус документа>
  date_ymd: <дата текущей содержательной версии>
  date_update: <дата обновления, если поле используется>
```

## Рабочие материалы и обучение экосистемы

Когда практика меняется, обновление документации меняет общий контекст людей и AI-агентов. Новая редакция связывает наблюдения, решения и правила следующего этапа развития.

В Team OS материалы пересмотра собираются как Notes в разрешённом списке «Новые версии документов» Management Layer. Задачи исполнения ведутся отдельно в Task Lists, итоги — в WorkLog Lists. Тип и маршрут проверяются по актуальному Core. Исторические стадии BASELINE, DRAFT и READY FOR PUBLICATION, а также прежние схемы копирования текста через ClickUp не определяют текущие операции с Task или Note.

Knowledge Substrate остаётся источником версионного текста и правил; Team OS связывает работу, обсуждения и результаты.
