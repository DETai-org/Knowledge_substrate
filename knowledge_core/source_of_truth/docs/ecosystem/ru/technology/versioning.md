# Версионность: процесс и стандарт

Версионность фиксирует состояние системы во времени: какой этап развития достигнут, какая редакция действует и где готовится следующая. Этот документ объединяет смысл версий проектов, выпускаемых компонентов и документов DET / DETai, форматы их номеров и правила фиксации новых состояний.

Версия может описывать проект, документ, правило, процесс или смысловую рамку. Её изменение означает признание нового устойчивого состояния. Версия повышается осознанно по решению ответственных, после завершения логического этапа; коммит, закрытая задача, deployment или прошедшее время сами по себе её не повышают.

## Версии проектов и SemVer

В классическом Semantic Versioning номер имеет три части: `MAJOR.MINOR.PATCH`, например `1.4.2`. В DET / DETai это отправная точка, а не универсальный формат для любого объекта.

Проектная версия фиксирует состояние решения; версия документа — редакцию знания или правила о нём. Release проекта не определяет статус описывающего его документа. В U.L.I. новую версию проекта признают после завершения значимого этапа и прохождения Release Fixation.

### 1. Что означает новая версия

Версия закрепляет результат завершённого этапа развития:

- **Достигнутое состояние** — что стало возможным и чем система теперь отличается от предыдущей фиксации.
- **Состав изменений** — ключевые возможности, исправления, архитектурные решения и выполненные Work Packages.
- **Вклад в экосистему** — какой продуктовый, технический, инфраструктурный, образовательный, управленческий или иной ресурс усилился.
- **Проверенную устойчивость** — на каких результатах приёмки основано решение о выпуске и какие ограничения известны.

Между официальными версиями проект может развиваться через любое число коммитов и обновлений production; они отслеживаются по Git SHA и operational evidence. Решение о версии связывает признание достигнутого состояния командой, понятное сообщение об изменениях участникам и пользователям и техническую фиксацию проверяемых артефактов.

### 2. Смысловая и техническая нумерация

Основная модель U.L.I. — **двухуровневая смысловая версия**:

```text
MAJOR.MINOR
```

| Пример | Значение |
| --- | --- |
| `0.1`, `0.2`, `0.x` | Завершённые этапы проекта, который ещё формируется; это не мешает внутреннему использованию. |
| `1.0` | Осознанное признание стабильного состояния, пригодного для устойчивой внутренней работы или публичной ответственности. |
| `1.1`, `1.2` и далее | Следующие устойчивые состояния через новые возможности, улучшения, исправления или архитектурное развитие. |

Переход к `1.0` **не требует** последовательного выпуска всех `0.x`. Номера отражают этапы зрелости, а не число PR. Решение о переходе к новому MAJOR или MINOR принимается по смыслу и результату Release Fixation, а не автоматически по правилам классического Semantic Versioning.

#### Техническая версия пакета

Инструменты публикации и форматы пакетов иногда требуют три компонента `MAJOR.MINOR.PATCH`. Это **техническое представление**, которое не меняет основную двухуровневую модель U.L.I.

Например, смысловая версия **Team OS Plugin 1.2** может соответствовать версии пакета **`1.2.0`**. Для нового смыслового этапа по умолчанию используется `PATCH=0`; следующий `PATCH` допускается для отдельного технического выпуска исправленного пакета без объявления этапа `1.3`.

Обычные изменения сервера или исходников, не сопровождающиеся переизданием пакета, не обязывают повышать его техническую версию. **Изменённый пакет нельзя выдавать за прежний идентичный выпуск**: при повторной публикации следует соблюдать правила версий используемого канала.

### 3. Один проект, несколько выпускаемых компонентов

В типичном технологическом контуре один репозиторий соответствует одному проекту. **Монорепозиторий не нарушает этот принцип**: один проект может содержать несколько взаимосвязанных, но самостоятельно выпускаемых компонентов (*releasable components*).

Компонент — это отдельная поверхность поставки или использования (например, Web, Plugin, Mobile), а **не новый самостоятельный проект**. Общие Core, API, библиотеки и база данных могут обслуживать несколько компонентов.

**Пример — [DETai Team OS](../management-layer/team-os/index.md)**: один проект и один монорепозиторий с несколькими компонентами.

| Компонент Team OS | Назначение | Версионирование |
| --- | --- | --- |
| **Web** | Интерфейс в браузере | Собственная последовательность релизов |
| **Plugin** | Интерфейс ChatGPT через MCP и skills | Собственная последовательность релизов |
| **Mobile** *(возможный будущий компонент)* | Мобильное приложение | Собственная последовательность релизов при его появлении |
| **Core/API** | Общий технологический фундамент | Версии контрактов и совместимости; отдельная линейка релизов необязательна |

Для таких компонентов допускается **Independent Versioning — независимое версионирование**: Web и Plugin могут иметь разные номера и даты выпуска, сохраняя единый `main` и общую историю Git. Каждое семейство релизов задаётся локальным стандартом проекта; например, в Team OS используются форматы `web/vX.Y.Z` и `plugin/vX.Y.Z`. Это примеры **форматов тегов**, а не утверждение, что конкретные теги уже опубликованы.

Любой Git-тег указывает на **коммит монорепозитория целиком**, даже когда обозначает выпуск одного компонента. Несколько тегов могут указывать на один SHA. Совместимость общих модулей проверяется для затронутых компонентов, но изменение Core не требует автоматически выпуска новых версий каждого интерфейса.

Общий принцип U.L.I. определяет, **когда состояние достойно версии**; особенности выпуска и технической фиксации определяются правилами соответствующего продукта.

### 4. Когда и как фиксируется релиз

Решение о новой версии принимается по завершении этапов производственного цикла:

```text
Project Intent → Work Model Planning → Implementation → Release Fixation
```

В Work Model Planning и Implementation работа проходит через Epic Issue, Work Packages, ветки и PR. На этапе **Release Fixation** проверяют достигнутое состояние, обязательные результаты, качество, совместимость и ограничения.

Основанием для новой фиксации может стать завершённая архитектура, важный Epic Issue, устойчивый пользовательский сценарий, устранение критического ограничения или новый вклад в экосистему. **Ни одно из этих событий само по себе не заменяет приёмку.**

Возможные решения: релиз одобрен, заблокирован или принят с документированными некритичными ограничениями. Порядок проверки и критерии определяет [Release Fixation Standard](production-cycle/release-fixation-standard.md).

После одобрения для соответствующего проекта или компонента фиксируются, когда применимы:

1. Точный Git SHA и Git tag.
2. GitHub Release с кратким **Release Summary**: достигнутое состояние, изменения, проверка, ограничения и переносимые задачи.
3. Ссылки на Epic Issue, Work Packages и PR.
4. README, release notes и production evidence, если они требуются.

**Коммит → deployment → Release Fixation — не обязательная последовательность на каждую правку.** Деплой может происходить без нового официального релиза; GitHub Release и deployment обозначают разные события.

Номер версии не заменяет оценку результата, а наличие тега не доказывает фактическую публикацию или обновление production.

### 5. Версия проекта и статус продукта

**Проект, репозиторий, выпускаемый компонент и продукт — разные понятия.** Версия сама по себе не делает внутреннюю систему рыночным продуктом.

- Внутренний инфраструктурный проект может иметь устойчивую `1.0`, оставаясь внутренним.
- Публичный продукт требует не только стабильной версии, но и определённых аудитории, ценности, доступа, ответственного за поддержку и показателей наблюдения.
- После публичного выпуска разработка продолжается в том же проекте. Следующий этап становится новой публичной версией только после отдельной Release Fixation.

В контуре репозиторных продуктов U.L.I. смысловая `1.0` рассматривается как технический порог стабильности, **но не как достаточное основание для продуктового статуса**.

## Номера версий документов

Для документов типов `explanation`, `standard`, `policy`, `tutorial`, `guide`, `how-to` и `reference` используется одноуровневая модель: `v1`, `v2`, `v3`.

Каждый новый номер обозначает содержательную редакцию. Исправления опечаток, форматирования и ссылок не требуют повышения версии, если смысл остаётся прежним. При смысловом изменении обновляются `descriptive.version`, даты и применимые связи; стабильный ID документа сохраняется.

Для философских документов с `layer: philosophy` и governance-документов, излагающих принципы, концепцию или доктрину, может применяться edition: `1st-edition`, `2nd-edition`, `3rd-edition`.

## Статус, нормативная сила и редакционная работа

| Что фиксируется | Где хранится | Значение |
|---|---|---|
| Жизненный цикл и версия документа | YAML metadata в Knowledge Substrate | `descriptive.status: active` — действующая редакция; `draft` — рабочий текст для review |
| Каноническая и нормативная сила | `governance.canonicality` | Определяется отдельным решением; статус `active` сам по себе не делает рабочую модель обязательной нормой |
| Подготовка и рассмотрение новой редакции | Ветка, PR и рабочие записи Team OS | Исходное состояние, новая редакция, review, готовность к публикации и опубликованный результат |

Остальные значения статусов определяет [политика metadata](../knowledge/metadata-policy.md). Статус Task, Note или PR не присваивает документу нормативную силу. Публикация файла также не переводит `draft/working` в `active/canonical` автоматически.

Работа над новой редакцией не отменяет опубликованную. Пока идёт review, действующая версия остаётся исходным состоянием; её не требуется переводить в `draft` только из-за появления PR.

## Как подготовить и опубликовать новую редакцию

1. Найти канонический Markdown-файл, проверить владельца, назначение и границы документа.
2. Зафиксировать исходное состояние ссылкой на файл и неизменяемый commit SHA. Git хранит версии; полнотекстовый дубликат в task-системе не обязателен.
3. Подготовить новую редакцию в рабочей ветке по правилам репозитория. Для документов экосистемы применяется маршрут `docs/ecosystem → main`.
4. При смысловом изменении повысить номер версии, обновить дату редакции и документальные связи, сохранив stable ID.
5. Провести содержательный review; проверить metadata, прямые ссылки, навигацию, публичность и сборку MkDocs.
6. Опубликовать редакцию через принятый PR-процесс и отдельно подтвердить изменения статуса или нормативной силы, если они требуются.
7. Связать рабочие материалы и итог с PR и опубликованной версией. Предыдущая редакция остаётся доступной в Git history.

В metadata содержательной версии указываются:

```yaml
descriptive:
  version: v<N>
  status: <подтверждённый статус документа>
  date_ymd: <дата текущей содержательной версии>
  date_update: <дата обновления, если поле используется>
```

## Рабочие материалы и обучение экосистемы

Когда практика меняется, обновление документации меняет общий контекст людей и AI-агентов. Новая редакция связывает наблюдения, решения и правила следующего этапа развития.

В Team OS материалы пересмотра собираются как Notes в разрешённом списке «Новые версии документов» Management Layer. Задачи исполнения ведутся отдельно в Task Lists, итоги — в WorkLog Lists. Тип и маршрут проверяются по актуальному Core. Исторические стадии BASELINE, DRAFT и READY FOR PUBLICATION, а также прежние схемы копирования текста через ClickUp не определяют текущие операции с Task или Note.

Knowledge Substrate остаётся источником версионного текста и правил; Team OS связывает работу, обсуждения и результаты.
