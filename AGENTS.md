# AGENT Instructions — Knowledge_substrate

## Общий контекст
Этот репозиторий — каноническая база знаний экосистемы DET / DETai.
Главная особенность: **папка `knowledge_core/source_of_truth/docs/` — это источник дополнительных контекстов**.
Если входные данные пользователя недостаточно ясны, **разрешено и рекомендуется** уточнять контекст, опираясь на документы из `docs/ecosystem/ru/ecosystem/`.

## Операционный log-summary

Основной маршрут — [WorkLog List Knowledge Substrate](https://team.detai-x.com/task-center/lists/c83e66a9-b3b7-5759-9a6d-cab349a2121b)
контура Knowledge Substrate в Scope Infrastructure. Не подменяй его одноимённым проектом или удалённым
legacy List из Projects. Датированные итоги сохраняй через `log-summary` как
WorkLog с явной workDate/timezone и отдельный personal checkpoint; локальные
`*log-summary.md` не создавай.

Используй Team-OS App: точный URL/UUID сначала разрешается через
`resolve_resource`, проект и Tasks/Notes/Logs — через `resolve_project` и live
Core registry. Проверь kind/contentKind родительского List перед create,
актуальную version и expectedVersion перед patch. UUID/название/иконка не
определяют тип и не дают прав.

Новая запись без уточнённого типа — Task в однозначном Tasks route; явная
заметка — Note; сводка — WorkLog и короткий personal checkpoint. При правке
выбранной Note/WorkLog сохраняется её тип. Task completion/assignees к Notes
и WorkLogs не относятся. Начальный контекст читается один раз по направлению,
а обычный CRUD не загружает полный Home повторно.

При OAuth отказе нужен reconnect/rescan, при отсутствующем маршруте — draft
и конкретная причина. ClickUp API, старый navigation YAML, mirror, DB и server
bearer не являются fallback. Исторические source IDs — provenance, не адрес
новой записи; текущий путь, тип и доступ подтверждает Core.

## Правила работы со ссылками на базу знаний (MkDocs)

Если в файлах репозитория встречается ссылка на документацию в формате публичного URL MkDocs (https://detai-org.github.io/), агент может получать её содержимое двумя способами: открывая страницу по указанному адресу или обращаясь к соответствующему файлу внутри репозитория.\
Поскольку база знаний MkDocs собирается из файлов, находящихся в папке `knowledge_core/source_of_truth/docs/ecosystem/`, такую ссылку можно рассматривать как указатель не только на внешнюю веб-страницу, но и на путь к документу внутри этой папки, при сохранении остальной структуры URL.
Рекомендуется использовать тот способ доступа, который в конкретной ситуации оказывается быстрее и продуктивнее для получения нужной информации.

## Локальный просмотр ветки или Pull Request в MkDocs

Фразы пользователя **«Подними MkDocs на текущей ветке»** и **«Покажи локально PR №…»** являются запросом на локальную визуальную проверку документации.

Перед переключением проверь `git status --short`. Не перезаписывай незакоммиченные пользовательские изменения: если рабочее дерево занято другой работой, используй отдельный `git worktree` или остановись и согласуй переключение.

Для просмотра Pull Request в чистой рабочей копии:

```powershell
gh pr checkout <PR_NUMBER>
py -m pip install -r requirements-docs.txt
py -m mkdocs serve --dev-addr 127.0.0.1:8000
```

Если локальная ветка PR уже существует, достаточно переключиться на неё и подтянуть изменения:

```powershell
git fetch origin
git switch <BRANCH_NAME>
git pull --ff-only
py -m mkdocs serve --dev-addr 127.0.0.1:8000
```

После запуска открой `http://127.0.0.1:8000/` и сообщи пользователю имя ветки, commit и прямую ссылку на проверяемую страницу. Если порт `8000` занят, сначала установи, что его использует MkDocs именно этого репозитория; не останавливай посторонний процесс. После смены ветки перезапусти сервер, чтобы сайт был собран из нового состояния.

На macOS и Linux используй `python -m ...` вместо Windows launcher `py -m ...`. Локальный сервер является только предпросмотром: он не публикует draft на основном сайте.

## Проверка публичности документации

Все файлы в `knowledge_core/source_of_truth/docs/ecosystem/` входят в публичную сборку MkDocs, включая все локали и поля YAML. Не публикуй прямые ссылки на приватные репозитории DETai, внутренние PR/коммиты/задачи или промежуточные файлы реализации. В пользовательской документации запрещён рассказ о конкретных merge/deploy/миграциях как доказательство доступности функции. Ссылайся на официальные публичные страницы, действующие правила и стабильную справку. Внутреннее происхождение решений фиксируй в закрытом owning-контуре, а не в MkDocs.

Перед коммитом проверяй все доступные языковые версии и выполняй `python scripts/check_public_docs_refs.py` и сборку MkDocs. В случае изменения статуса пилот → production сначала подтверди реальное состояние, затем синхронно обновляй публичные документы, не опережая релиз.

## Правило внесения правок в документы экосистемы

Если задача требует добавить, изменить или уточнить файлы внутри `knowledge_core/source_of_truth/docs/ecosystem/ru/ecosystem/*`, правки сначала вносятся в сборочную ветку `docs/ecosystem` и публикуются через актуальный pull request `docs/ecosystem → main`.

Не вносить такие изменения напрямую в `main`: сначала переключиться на `docs/ecosystem`, перенести или выполнить правки там, а уже затем готовить их к публикации через соответствующий pull request.
